Adding Development Standards to Claude Code's Knowledge Base

How to give Claude Code persistent awareness of your team's coding conventions, architecture decisions, and project rules — so it never starts from zero again.

Based on official docs

Official Reference

How Claude Code Memory Works

Every Claude Code session starts with a blank context window. Claude doesn't remember yesterday's conversation about your coding conventions, folder structure, or test commands. Two mechanisms carry knowledge across sessions:

📄 CLAUDE.md Files

Instructions you write that Claude reads at every session start. Think of them as a README that Claude reads before touching a single line of code.

🧠 Auto Memory

Notes Claude writes for itself based on your corrections and discoveries. Build commands, debugging insights, architecture notes it picks up over time.

For injecting your team's development standards, CLAUDE.md files are the primary tool. Auto memory is complementary — it captures things Claude learns on its own.

Part 1 — Where to Put CLAUDE.md Files

CLAUDE.md files can live in several locations. Each location has a different scope and audience.

Scope File Path Who It Affects Git?
Organization /etc/claude-code/CLAUDE.md (Linux)
/Library/Application Support/ClaudeCode/CLAUDE.md (macOS)		 Every developer, every machine Deployed via MDM / Ansible
Project (shared) ./CLAUDE.md or ./.claude/CLAUDE.md Everyone on the team, in this repo Yes
User (personal) ~/.claude/CLAUDE.md Only you, across all projects No
Local ./CLAUDE.local.md Only you, in this repo No (add to .gitignore)
How they stack

All CLAUDE.md files are combined, not overridden. Claude reads them from broadest scope (organization) to narrowest (local). If two files contradict each other, Claude may pick either arbitrarily — so avoid conflicting rules.

Part 2 — Creating Your First CLAUDE.md

Option A: Auto-generate with /init

Open Claude Code in your project directory and run:

/init

Claude analyzes the codebase and generates a starting CLAUDE.md with build commands, test instructions, and conventions it discovers. If a CLAUDE.md already exists, /init suggests improvements rather than overwriting.

Option B: Write It Manually

Create a file named CLAUDE.md at your project root. Here's a realistic example:

CLAUDE.md# Project: payments-api

## Build & Run
- Install dependencies: `pnpm install`
- Run dev server: `pnpm dev`
- Run all tests: `pnpm test`
- Run single test file: `pnpm test -- path/to/file.test.ts`
- Build for production: `pnpm build`

## Architecture
- Monorepo managed by Turborepo
- API handlers live in `packages/api/src/handlers/`
- Shared types in `packages/shared/types/`
- Database layer in `packages/db/` — never access the DB directly from handlers

## Code Standards
- Use TypeScript strict mode everywhere
- 2-space indentation, no tabs
- Named exports only — no default exports
- All functions must have JSDoc comments with @param and @returns
- Error handling: always use our custom AppError class
- No `any` types — use `unknown` and narrow instead

## Testing
- Every handler needs unit tests AND integration tests
- Integration tests use the test database, not mocks
- Test file naming: `*.test.ts` next to the source file
- Minimum 80% coverage on new code

## Git Conventions
- Branch naming: `feat/TICKET-123-short-description`
- Commit messages: conventional commits (feat:, fix:, chore:)
- Always rebase on main before opening a PR
- Squash merge only

## API Design
- RESTful endpoints under `/api/v1/`
- Always validate input with Zod schemas
- Return standard envelope: `{ data, error, meta }`

## Do NOT
- Never modify files in `packages/db/generated/` — auto-generated
- Never commit .env files
- Never use `console.log` in production code — use the logger

What Makes Good CLAUDE.md Content

✓ Include

  • Build, test, and lint commands (exact commands)
  • Directory structure and what lives where
  • Naming conventions and code style rules
  • Patterns to follow (error handling, API design)
  • Things Claude should never do

✗ Exclude

  • Things Claude learns on its own after one session
  • Information that changes weekly (use prompts)
  • Secrets, API keys, or sensitive data
  • Long procedures or tutorials (use skills)
Keep it under 200 lines

Longer files consume more context tokens and reduce how reliably Claude follows the instructions. If your standards are growing large, split them into path-scoped rules.

Part 3 — Organizing with .claude/rules/

When your standards grow beyond a single CLAUDE.md, split them into modular rule files. Rules can be scoped to specific file patterns so they only load when relevant.

your-project/ ├── .claude/ │ ├── CLAUDE.md # Main project instructions (brief) │ └── rules/ │ ├── code-style.md # TypeScript/linting standards │ ├── testing.md # Testing conventions │ ├── api-design.md # API patterns and requirements │ ├── security.md # Security rules │ ├── frontend/ │ │ ├── components.md # React component standards │ │ └── styling.md # CSS/Tailwind conventions │ └── backend/ │ ├── database.md # DB access patterns │ └── auth.md # Authentication rules

Path-Scoped Rules

This is the most powerful feature for large codebases. Add a paths field in YAML frontmatter to load rules only when Claude works with matching files:

.claude/rules/frontend-components.md---
paths:
  - "src/components/**/*.tsx"
  - "src/components/**/*.ts"
---

# React Component Standards

- Use functional components with hooks only — no class components
- Every component must have a Props interface above the component
- Event handler naming: `handleEventName`
- State naming: `[noun, setNoun]`
- All components must have a corresponding `.test.tsx` file
.claude/rules/database.md---
paths:
  - "packages/db/**/*.ts"
  - "src/repositories/**/*.ts"
---

# Database Standards

- All queries go through repository classes
- Never write raw SQL — use the query builder
- Every write operation must be wrapped in a transaction
- Always include created_at and updated_at timestamps
- Soft delete only — set deleted_at instead of removing rows
.claude/rules/api-tests.md---
paths:
  - "**/*.test.ts"
  - "**/*.spec.ts"
---

# Testing Rules

- Use describe/it blocks, not test()
- First describe block matches the module name
- Use factory functions for test data, not hardcoded objects
- Clean up test database after each suite with afterAll()
- Never skip tests with .skip unless there's a TODO explaining why

Supported Glob Patterns

PatternWhat It Matches
**/*.tsAll TypeScript files in any directory
src/**/*All files under src/
*.mdMarkdown files in the project root only
src/components/*.tsxReact components in one specific directory
src/**/*.{ts,tsx}TypeScript and TSX files under src/

Part 4 — Importing Existing Documents

If you already have standards documented in other files, you don't need to duplicate them. Use the @ import syntax inside CLAUDE.md:

CLAUDE.md# Project Standards

See @docs/coding-standards.md for our full code style guide.
See @docs/api-design-guide.md for API conventions.
See @docs/git-workflow.md for branching and PR process.

## Quick Reference (always loaded)
- Run tests: `pnpm test`
- Lint: `pnpm lint`
- Build: `pnpm build`
Important caveats

Imported files load into context at launch — they don't reduce token usage, they just help with organization. Relative paths resolve relative to the importing file. Maximum import depth is 5 levels.

For Standards That Are Too Long

If your standards are extensive (30+ pages), don't import them all. Instead, tell Claude to read them on-demand:

CLAUDE.md# Architecture References

When working on the API layer, read @docs/api-architecture.md before making changes.
When working on the database schema, read @docs/database-design.md first.
When modifying auth flows, read @docs/security-model.md first.

This tells Claude to read the document when needed rather than loading everything into every session.

Importing AGENTS.md

If your repository already uses AGENTS.md for other AI coding tools, import it so both tools share the same instructions:

CLAUDE.md@AGENTS.md

## Claude Code Specific
Use plan mode for changes under `src/billing/`.

Part 5 — Auto Memory

While you write CLAUDE.md, Claude writes auto memory notes for itself. It decides what's worth remembering: build commands, debugging insights, code style preferences you corrected, architecture notes.

Where Auto Memory Lives

~/.claude/projects/<project-name>/memory/ ├── MEMORY.md # Index file (first 200 lines loaded per session) ├── debugging.md # Topic-specific notes ├── api-conventions.md # Topic-specific notes └── ...

Managing Auto Memory

ActionHow
View what Claude savedRun /memory in a session
Edit or delete notesThey're plain markdown files — open and edit directly
Toggle on/offRun /memory and use the toggle, or set "autoMemoryEnabled": false in project settings
Disable via env varCLAUDE_CODE_DISABLE_AUTO_MEMORY=1
Auto memory requires version 2.1.59+

Check your version with claude --version. Auto memory is on by default in supported versions.

Part 6 — Team Rollout Plan

Here's a step-by-step plan for rolling out Claude Code knowledge across your team.

1

Create the project CLAUDE.md

Add a CLAUDE.md to the repo root with essential project info. Keep it under 200 lines. Include build commands, architecture overview, and immutable rules.

2

Move detailed standards into .claude/rules/

Split your existing standards documents into focused rule files. Use path-scoping so rules only load for relevant files.

3

Commit to version control

git add CLAUDE.md .claude/rules/
git commit -m "chore: add Claude Code project instructions and rules"
4

Set up personal preferences

Each developer creates their own CLAUDE.local.md (gitignored) for personal preferences like local ports, verbose variable name preferences, etc.

5

Review and iterate

After a few weeks: run /memory to see what Claude auto-learned, promote useful entries into CLAUDE.md, remove redundancies, check for conflicting rules.
