Summary

The existing UserAccount microservice moves from Azure to AWS with the same 17 endpoints, the same SQL Server database and stored procedures, and the existing Serilog logging. Only the Azure services underneath change.

ComputeECS Fargate (ARM64) behind an internal ALB; more microservices (Study, Radiologist, others) join the same cluster later
Entry pointCloudFront, then API Gateway HTTP API with a Cognito JWT authorizer, a VPC Link to the private ALB
IdentityAmazon Cognito replaces Azure AD B2C; invite-only, MFA required, admin staff only
DatabaseAmazon RDS for SQL Server 2022, Multi-AZ in prod; the existing RadsForVets schema and 11 stored procedures run unchanged
Email, push, secretsSES (later), AWS IoT Core (recommended), Secrets Manager replace SendGrid, Azure Web PubSub, Key Vault
DeliveryCode stays in Azure DevOps; Azure Pipelines deploys to AWS with OIDC, no stored keys
Environmentsdev and prod in one shared account, separate VPCs, every resource prefixed {env}-radiaflow-
Hostnamesradiaflow-dev.medilis.ai and radiaflow.medilis.ai; DNS stays at Namesilo

What changed from the first draft. The draft used PostgreSQL to avoid SQL Server licensing. The service depends on SQL Server features (symmetric-key encryption, AT TIME ZONE, sys.time_zone_info, dynamic SQL) and on tables shared with other services, so SQL Server stays and the licence cost returns. The draft's SQS logging pipeline and Backoffice portal are also dropped: the existing Serilog logging is reused and there is no permission layer in this phase.

Not in these numbers

  • Future microservices: each extra Fargate service adds about $15 to $60 a month, depending on size and task count. The database is shared.
  • SES (cents per thousand emails), AWS DMS for the one-time data move, an AWS support plan, Azure DevOps costs, Namesilo, VAT.
  • The current Azure SQL bill, which is needed to compare (open item 19).

Ways to lower it

  • Run the dev database on a VM with SQL Server Developer or Express, which have no licence fee. This saves about $745 a month.
  • Right-size the prod database. Start with db.m6i.large Multi-AZ and scale up only if the load needs it. This alone saves about $1,700 a month.
  • Check the newer RDS instance generations. AWS announced in December 2025 SQL Server instances that optimize CPU for up to 55% lower price; the design uses the older M6I class.
  • Reserved pricing. Reserve the prod database for 1 or 3 years once the size is stable.
  • Dev schedule. Stop the dev database outside working hours (compute billing stops, storage continues; RDS restarts a stopped instance after 7 days).
  • Skip interface endpoints in prod if NAT data volume stays low, saving about $86.

Architecture

Every API call is authenticated at the edge before it reaches a private service. The dev VPC is shown in detail; prod has the same layout and is not peered with dev. Dashed orange tiles are future microservices in the same ECS cluster.

ECS injects the origin-verify secret and the database connection strings from Secrets Manager when a task starts, so the backend reads them as ordinary settings and does not call Secrets Manager itself.

Header mapping and defence inside the VPC

  • API Gateway overwrites X-User-Id from the verified token and sets a static X-Origin-Verify secret (generated by CDK, stored in Secrets Manager for the services). Overwriting means a client-supplied X-User-Id is always replaced.
  • API Gateway cannot read Secrets Manager at request time, so the origin secret is a static value in the integration; rotating it means redeploying the integration. Verify the exact claims variable ($context.authorizer.claims.<name>) on the first deployment.
  • Defence layer 1: the ALB is internal and its security group accepts only the VPC Link group.
  • Defence layer 2: a middleware rejects requests without the right X-Origin-Verify value with 403, using a constant-time comparison.

RDS settings

  • Edition: SQL Server 2022 Standard (Enterprise only if a feature needs it), license included, Multi-AZ in prod. Web and Express editions do not offer Multi-AZ. Compatibility level 160.
  • Instance class: M6I or R6I family. SQL Server on RDS has no Graviton option, so the database is the one x86 component; the Fargate tasks stay ARM64. Newer optimize-CPU generations may be cheaper (see Monthly cost).
  • Time zone: set to UTC at creation; it cannot be changed later. The stored procedures use GETDATE() and Azure SQL runs in UTC.
  • Database name: keep RadsForVets; UserTosSelect reads [RadsForVets].[dbo].[vw_mst_tos_active] by a three-part name.
  • Symmetric-key encryption: UserDetails_Key and the certificate Rads4Vets live inside the database. The creation script and certificate backup are not available, so production data moves by a one-time decrypt-and-re-encrypt copy: create a new key and certificate on RDS, read each encrypted column through the existing key on Azure SQL, write it back with the new key. About 84 stored procedures and scripts reference this key (users, clinics, physicians, radiologists, studies, chat, billing), so this is a database-wide job. This is the biggest technical risk.
  • Backups: automated backups with point-in-time recovery (up to 35 days) plus a manual snapshot before each production migration. The SQLSERVER_BACKUP_RESTORE option with an IAM role for an S3 bucket supports native backups from the test SQL Server; production Azure SQL Database cannot write native backups and needs a BACPAC or ETL copy.
  • Encryption at rest: KMS storage encryption. Credentials: RDS-managed master secret with rotation; service logins stored as separate secrets.
  • Migrations: versioned, idempotent T-SQL scripts (CREATE OR ALTER) run by a one-off ECS task in the pipeline, never at application start-up.

How to set it up

  1. Create one EC2 instance in a private DB subnet with no public IP: dev-radiaflow-sqlvm, t3.large (Developer) or t3.medium (Express), encrypted gp3 volume of at least 100 GB.
  2. Use security group dev-radiaflow-sg-sqlvm that allows port 1433 only from dev-radiaflow-sg-ecs. Reach the machine for administration through AWS Systems Manager Session Manager, not RDP or SSH over the internet.
  3. Give the machine the role dev-radiaflow-role-sqlvm (Session Manager, read and write on the dev backup bucket, read on its own secret).
  4. Install SQL Server 2022 (Developer or Express), set the Windows time zone to UTC, collation to match the current database, and enable TCP on 1433.
  5. Restore or copy RadsForVets and create the log schema; create the logins radiaflow_useraccount and radiaflow_migrator; copy the encryption key set-up used on RDS.
  6. Store the connection strings in the existing secrets /dev/radiaflow/db/useraccount and /dev/radiaflow/db/log, pointing at the VM's private address. The service code does not change.
  7. Back up: a daily snapshot policy dev-radiaflow-dlm-sqlvm for the volume, plus a native backup to dev-radiaflow-sql-backups-… before each pipeline migration run. Stop the VM outside working hours if you want to save more.

Parity risk. If dev runs on a VM, the pipeline never exercises RDS before prod. Before the prod cutover, validate the migration once on a temporary RDS instance (create it, run the key copy and the 11 stored procedures, delete it). It costs a few dollars and removes the biggest surprise. This is step 8a in the build order.

Prod stays on Multi-AZ RDS in every case. Run only one dev database at a time: either RDS or the VM, not both.

Migration and rollout

  1. Provision the stacks in staging.
  2. Move the database. The test SQL Server 2022 can use a native .bak through S3. Production is Azure SQL Database, which cannot write native backups: use a BACPAC or an ETL copy, and because a BACPAC does not carry certificates and the key script is not available, use the decrypt-and-re-encrypt copy described under Database.
  3. Run UserSelectById, UserSearchByEmail and UserSelect on RDS and compare with Azure SQL for a sample of users.
  4. Create the Cognito pool with custom attributes custom:user_id and custom:company_id (immutable after creation, so decide names first), then import users from B2C with FORCE_CHANGE_PASSWORD.
  5. Deploy UserAccount.Aws.Microservice behind API Gateway; point the SPA at the Cognito hosted UI.
  6. Run the regression checklist in staging, then cut over; keep the Azure service and B2C available for rollback until sign-off.

Regression checklist

  • Register a user: Cognito user, mst_user row, SES email received, first sign-in forces a password change.
  • Exists checks: known email, unknown email, email only in SQL Server.
  • GetUserById: session row created, clinics returned for type 6, push-channel URL works.
  • Disable then enable: sign-in blocked and restored; active sessions revoked on disable.
  • Update user: name, email and company change appear in Cognito and mst_user.
  • Reset password (with and without email), delete user, clinic link removal.
  • GetUsers: paging, sorting, each filter, company scoping.
  • Token validation: expired, wrong issuer and tampered tokens return 401.

Naming convention

Every resource is named {env}-{sys}-{resource}, with the environment first so dev and prod sort apart in every console. {sys} is a placeholder set to radiaflow; every name below is built from it by one helper, so changing the placeholder renames everything at the next deploy.

  • Keep {sys} at 12 characters or fewer; ALB and target group names cap at 32.
  • No region in names except S3; no account id anywhere else.

Baseline for every bucket

  • Block Public Access at account and bucket level; ACLs disabled (bucket owner enforced).
  • Bucket policy denies requests without TLS and, for private buckets, any principal outside the environment's roles.
  • Default encryption on; SSE-KMS with the environment's key for sensitive data (backups).
  • Lifecycle rule that aborts incomplete multipart uploads after 7 days, plus the expiry rules above.
  • Tags as above; DataClass = restricted for SQL backups.
  • Removal policy RETAIN in prod and for SQL backups everywhere; dev SPA and static buckets may auto-delete.
  • Data stays in il-central-1: no cross-region replication.
  • Turn on IAM Access Analyzer for S3 and review findings monthly.

Key layout: SPA build at the bucket root; static content under email-templates/; backups under RadsForVets/{yyyy}/{mm}/; access logs under alb/, cloudfront/, s3/. Retention values are proposals to confirm against the audit policy.

Flow

One multi-stage pipeline, radiaflow-useraccount, runs on pushes to main that touch the UserAccount project, Microservices.Common or the infrastructure folder. Dev deploys automatically; prod needs a manual approval, so no separate prod branch is required (existing Azure pipelines on a prod branch stay as they are).

The front end uses a second, shorter pipeline: build the React app, sync it to the SPA bucket, invalidate CloudFront. The database migration runs inside AWS as an ECS task because RDS has no public access; the pipeline only starts the task and waits for its exit code.

Authentication without stored keys

  1. In AWS, create an IAM OpenID Connect provider for Azure DevOps (one per account; reuse it if it exists).
  2. Create one deploy role per environment, dev-radiaflow-role-deploy and prod-radiaflow-role-deploy. Each trust policy accepts only the matching service connection, so the dev connection cannot assume the prod role.
  3. In Azure DevOps, create the AWS service connections aws-radiaflow-dev and aws-radiaflow-prod with the OIDC option and the role ARN. This needs the AWS Toolkit for Azure DevOps extension.
  4. No access keys or secrets are stored in the pipeline.

Building the ARM64 image the easy way

Use Microsoft-hosted Ubuntu agents and a two-stage Dockerfile: compile on the agent's own x64 architecture with -r linux-arm64, and make the final stage only COPY files onto the ARM64 runtime image. Nothing runs under emulation, so the build is as fast as an x64 build and no self-hosted agent is needed. Do not add RUN commands to the final stage. Check that Microservices.Common publishes cleanly for linux-arm64 (open item 5).

Quality gates and rollback

  • Pull requests build and test but do not deploy.
  • cdk diff output is attached to the run so a reviewer sees infrastructure changes before the prod approval.
  • ECS rolling deployment with the circuit breaker rolls back a failing release; a failed migration stops the pipeline before prod.
  • To roll back, redeploy the previous image tag; migrations are idempotent and forward-only, so database changes are corrected by a new migration.
  • The pipeline fails on critical image scan findings and on vulnerable NuGet packages.
  • Decided: the dev team group (Vigen, Gera) creates the AWS service connections, installs the AWS Toolkit extension and approves prod deployments, with self-approval off so the other person signs off.
